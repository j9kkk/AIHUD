可行性调研 · 架构方案 · v1

AI 额度 HUD：把各渠道额度放进状态栏，且随时可以彻底消失

目标：Windows / macOS / iOS / Android 原生呈现 Codex、Claude、Gemini、WorkBuddy 等渠道的剩余额度； 常驻但不打扰，不需要时 0 占用。本文回答两件事：这条路可信吗、系统怎么搭。
调研日期 2026-10-30 桌面端：已有两个 MIT 开源先例 移动端：无第三方状态栏 Gemini 旧接口 2026-06-18 已停服 本轮未用真实账号打通端点

00先说结论

四句话，按重要性排序。后面每一节都在给这四句话提供证据。

桌面端可行
macOS / Windows

不是一个猜测：CodexBar（MIT，macOS 14+，已注册 110 个 provider）与 OpenTokenUsage（MIT，Windows 11）已经把"菜单栏 / 托盘显示额度"完整做出来了，端点和解析逻辑公开可查。

移动端形态不同
iOS / Android

iOS 没有第三方状态栏，只能做小组件 + 灵动岛 + 控制中心；Android 能做真·常驻，但必须常驻前台服务通知。两者都做不到"桌面那种一像素常驻"。

渠道里有雷
Gemini / WorkBuddy

Gemini 个人账号的额度接口已于 2026-06-18 停服，必须改走 Antigravity；WorkBuddy 虽无公开文档，但其设备登录流已实测可用（见用户故事规格第 07 节），不再属于"只能抓包"。

风险不在技术
在"非官方端点"

所有渠道都是反向工程出来的未公开接口，两个开源项目自己在文档里都写着"随时可能变"。所以架构的核心不是"多快拿到数据"，而是"某个渠道坏掉时，其余照常"。

01平台能力：哪些平台真能"常驻 + 完全隐藏"

"状态栏"在不同系统上不是同一个东西。下表按"用户实际能看到的载体"逐平台核对，并标注系统硬限制。

平台常驻载体"完全隐藏"怎么做系统硬限制（必须接受）判断
macOS 14+ 菜单栏 NSStatusItem；SWiftUI 的 MenuBarExtra 可做但需 AppKit 兜底 一键隐藏 / 只留图标 / 拖出可见区；可无 Dock 图标，纯后台驻留 macOS 26（Tahoe）起状态栏项由 Control Center 托管，并存在按 bundle id 的抑制/黑名单（CodexBar #3377、SketchyBar #789 均为真实案例） 高
Windows 11 通知区域托盘图标（Shell_NotifyIcon）+ 可选任务栏贴条（AppBar 覆盖层） 拖进托盘溢出区即隐藏；贴条可单独关；全局快捷键唤出面板 Windows 没有"状态栏"这个概念，贴条属实验性土办法；未签名安装包会触发 SmartScreen（OpenTokenUsage 实测需用户点"仍要运行"） 高
Android 13+ 前台服务常驻通知（ongoing，不能滑掉）+ 快捷设置磁贴 + 桌面小组件 关闭监控 → 通知/磁贴/小组件同时消失；通知可折叠到最简一行 Android 13+ 需 POST_NOTIFICATIONS；Android 14+ 前台服务必须声明类型；国产 ROM 省电策略仍可能杀后台 中高
iOS 18+ 主屏/锁屏小组件（WidgetKit）、灵动岛 Live Activity、控制中心控件（ControlWidget） 移除小组件 = 零打扰；控制中心控件平时完全不可见 没有任何第三方状态栏 API。后台刷新由系统调度，不能保证准时；Live Activity 需要"进行中的活动"且有时长上限 中
Linux（可选） Qt / StatusNotifier 托盘 隐藏托盘图标 各桌面环境实现不一；但有现成开源实现可参考 高
结论修正：把"状态栏常驻"当成四个平台的同一件事，会在移动端撞墙。建议统一为产品语言——"一瞥可见（Glanceable）"：桌面用状态栏，Android 用常驻通知，iOS 用灵动岛/小组件/控制中心。三者共用同一套"L0 隐藏 / L1 徽标 / L2 面板"可见性模型。

03架构：五层 + 一条信任边界

设计原则只有一条：凭据和额度快照不出本机；所有跨平台差异压缩到薄壳里，核心只产出一种数据。

■ 为什么把适配器独立成插件

  • 五个渠道是五种完全不同的鉴权与解析逻辑，生命周期完全不同
  • 某一渠道被上游改接口时，只需停用该插件，不影响其它卡片
  • 新增渠道（Cursor、Copilot、Antigravity）不改核心

■ 为什么核心要跨平台同构

  • 额度计算、退避、Pace 判定只有一份代码，避免五个平台五种口径
  • 同一份 QuotaSnapshot 喂给托盘、通知、小组件
  • 本地只读 API（127.0.0.1）让脚本/其它 App 也能复用

■ 移动端的硬约束

  • 手机上没有桌面的 CLI 登录态，拿不到同一份凭据
  • 所以只有两条路：桌面作 Hub 局域网同步，或 E2E 加密中继
  • 红线：明文 refresh token 绝不上云，只同步数值

04「常驻但不打扰」怎么写进规格

这是需求里最容易被做成形容词的部分。把它变成三档状态 + 四条触发规则，验收就能客观核对。

可见性桌面形态AndroidiOS
L0 隐藏托盘/菜单栏无图标，进程仍活在后台；快捷键或 Spotlight 可唤起前台服务停止，通知消失无小组件、无 Live Activity
L1 徽标单图标 + 一个数字（最紧张的那条额度），hover 出摘要通知折叠为一行：Claude 82% · 2h13m 复位灵动岛紧凑视图 / 锁屏一行
L2 面板点开：各渠道窗口 + 复位倒计时 + 超额积分 + 状态徽标展开通知或点磁贴小组件中号/大号，或控制中心控件展开
规则 1 · 越线才出声

用量 ≥ 80%，或按当前消耗速度会在复位前耗尽 → 自动从 L0 升到 L1 并弹一次通知。其余时间保持用户设定的档位。

规则 2 · 专注模式闭嘴

全屏应用 / 勿扰 / 专注模式期间不弹任何通知，只更新数字；退出后补一条汇总，不逐条补。

规则 3 · 复位前提醒

复位前 30 分钟提示一次"额度即将重置，可放心开长任务"。这是用户真正的决策点。

规则 4 · 过期必须自曝

数据超过 3 个轮询周期未更新 → 卡片显示"12 分钟前"并降低不透明度，绝不拿旧数字冒充实时，也不静默归零。

验收方式

用可脚本化的断言代替肉眼：分辨率/DPI、深色与浅色、L0 时进程 CPU 占用、通知是否出现在勿扰、过期标注是否存在。

冷启动预算

首屏从进程启动到出数字 ≤ 1.5s（读缓存先显示，再刷新）；空状态 ≤ 200ms 出骨架。

06技术选型：两条路，成本差一倍

A · 原生 ×5
Swift / SwiftUI · C# WinUI3 · Kotlin Compose · SwiftUI(iOS)

体验最好，状态栏/托盘/通知/小组件都是第一等公民。代价是额度逻辑写 3~4 遍，渠道一改接口要改多处；1 人做不完。

适合：先把 macOS + Windows 做到极致，移动端后置。

B · 共享核心 + 原生薄壳（推荐）
Rust 核心（HTTP + 解析 + 缓存 + 退避）· Tauri 桌面壳 · Kotlin/Swift 移动壳

额度逻辑只写一次，五个壳只负责"把数字画出来"。Tauri 托盘在桌面端成熟；移动端小组件/灵动岛本来就必须原生写，正好只写壳。

适合：想一次覆盖多平台、且接受 Windows 体积略大（~10MB）。

建议：选 B。理由不是"技术更优雅"，而是这个项目的维护成本 90% 花在跟进上游接口变化——把这件事收敛到一个 Rust crate 里，等于把长期成本砍掉 3/4。

08本轮验证边界（必须诚实说明）

已核实：平台能力（Apple / Microsoft / Google 官方文档）、Gemini 停服公告、两个开源项目的端点文档与凭据位置、macOS 26 状态栏问题的一手 issue。

未核实：没有用任何真实账号打通端点——本机出网受限（api.anthropic.com 探测返回 403，chatgpt.com / cloudcode-pa / gemini.google.com 均连接失败），也没有安装 Claude Code / Codex CLI 的登录态。

因此：P0 的第一件事不是写 UI，而是在一台已登录的 Mac 和 Windows 上跑一遍"四端点健康检查"（Claude usage、Codex wham、Antigravity agy、WorkBuddy 抓包），把返回体固化成 fixture。这一步 1 天能完成，但它决定后面所有排期。
