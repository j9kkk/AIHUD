# 风险与最小验证（v2；v1 见 RISKS.v1.md）

你已确认三个渠道都能长期保活，并且有可参照的实现。原先的“挂机 72 小时”**取消**。剩下的风险从“这条路走不走得通”，变成了“**我们是否照着参照实现做对了**”，可以在几分钟到几小时内验证完。

---

## R1（最高）：协议细节与参照实现不一致

**未知项**：我们的授权和续期请求，在端点、请求体格式、请求头、scope、续期时机和错误分类上，能否与 CLIProxyAPI / workbuddy2api 逐项一致。

**为什么它的风险最高**：上一轮 Claude 卡在 429、Codex 凭据过期，都发生在这一层。对照后已发现至少 6 处差异：
1. Claude 回调方式不同（粘贴码 vs 本机回调）。
2. Claude scope 不同。
3. Claude User-Agent 不同。
4. 网络错误时的重试策略会导致 refresh_token 被消费。
5. WorkBuddy 没有监控 refreshExpiresAt。
6. WorkBuddy 缺少 X-Enterprise-Id 和 X-Tenant-Id。

详见 REFERENCES.md。

**最小验证（约 2 小时代码 + 你操作 5 分钟）**
1. **先写 Core 层和 CLI**，不碰任何界面：`aihud auth <渠道>`、`aihud usage`、`aihud refresh --force <账号>`。
2. 写一个**协议对照测试**：用本地假服务器拦截请求，逐字段断言我们发出的请求与 REFERENCES.md 中的参照实现一致，包括 URL、方法、Content-Type、请求体字段、关键请求头。
3. 你用真实账号把三个渠道各授权一次，然后运行 `aihud refresh --force`，**当场强制续期一次**，再运行 `aihud usage` 读数。

**通过标准**：三个渠道都能完成「授权 → 读数 → 强制续期 → 用新 token 再读数」，并且官方客户端没有被踢下线。

**这一步通过之前不写 UI。**

## R2：额度接口的字段随套餐不同

**未知项**：Pro / Max / Plus / Team 等不同套餐、WorkBuddy 国内站与国际站，返回的字段是否一致。

**最小验证**：R1 完成后，`aihud usage --dump` 把每个账号的原始返回体（脱敏）存成 fixture，解析器对这些 fixture 跑单元测试。这一步零额外成本。

## R3：界面形态

**最小验证**：你在 `samples.html` 的三个样例里选一个（或者指出要改的地方）。之后的视觉验收以选定的样例为准。

## R4：macOS 26 状态栏图标被系统抑制

**最小验证（15 分钟）**：先做一个只有图标的空应用，用 ad-hoc 签名，在你的机器上测试三种情况：直接启动、重启后自启、菜单栏拥挤时。CodexBar 对此问题有现成的诊断和规避方法（`docs/status-item-diagnostics.md`，以及固定 autosave 名称）。
